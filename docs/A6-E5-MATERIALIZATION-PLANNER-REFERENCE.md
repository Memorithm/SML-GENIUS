# A6-E5 — Planificateur d'exécution DIRECT vs table booléenne compacte

**Étape matérielle Rust vérifiable, sans benchmark matériel ni performance linguistique revendiqués.** SML-GENIUS a déjà `WideAnfGate`, une exécution par monômes GF(2) et un graphe de préfixes partageant les AND. Ce composant `sml_core::anf_e5_materialization` n'en crée pas une copie concurrente. Il fournit un **plan d'exécution** fondé sur des coûts mesurés à fournir par le caller, plus une matérialisation optionnelle `2^d` en bits empaquetés seulement lorsque l'amortissement prévu est strictement favorable.

Le critère d'autorisation est `Q * t_direct > t_compile + Q * t_lookup` ; tout ce qui ne satisfait pas ce test reste en mode `Direct`. Un coût CPU inférieur à celui du contrôle RAW ou ANF ne peut pas être déduit sans **mesures sur le matériel réel** : les tests utilisent des coûts *synthétiques* uniquement pour vérifier la logique des seuils.

**Contraintes de capacité :** fan-in `d≤16`, source physique `≤4096` cases booléennes de scratch, table `2^d` bits, allocation par blocs de 8 `u64` chacun alignés à **64 octets** avec `#[repr(align(64))]` sur le type réellement contenu dans `Vec`. Le code vérifie la position du pointeur de données modulo 64, la capacité allouée effective, les octets de métadonnées et les budgets distincts RAM et cache L3 (les valeurs de budget ne sont **pas détectées** automatiquement). Si RAM/L3 ou fan-in ne permettent pas la table, retour au chemin DIRECT sans allocation exponentielle. L'allocation temporaire du vecteur source est également plafonnée.

**Oracle indépendant :** la compilation énumère toutes les affectations locales jusqu'à `2^d`, demande à `WideAnfGate::evaluate_scalar` la vraie valeur booléenne, l'encode bit par bit dans les blocs de 64 octets, puis le lookup doit coïncider pour tous les contextes contrôlés. Cette première version est une **matérialisation de table**, pas encore une preuve que la transformée Pascal/Möbius donne une compilation plus rapide que cette référence. Le moteur Pascal pourra ensuite proposer une autre méthode de construction dont les sorties seront comparées à ce même oracle.

**Contrôles natifs :** source physique discontinue, sortie bit-à-bit identique, alignement du buffer alloué, coûts en mémoire réels, sélection directe lorsque Q est insuffisant ou L3 saturé, rejet de profils invalides et d'un fan-in supérieur au plafond. La CI GitHub-hosted exécute fmt/check/Clippy strict/tests avant toute fusion.

Ce composant ne fait **aucune** prédiction sur le TEST Flaubert gelé ni ne remplace le protocole E4. Pour un déploiement, il faudra des coûts `t_direct`, `t_lookup`, `t_compile` mesurés sur x86/ARM/Thor, une comptabilité cache réelle et la comparaison du débit avec le moteur sparse `WideAnfGate` ; pas de mesure GPU ni de supériorité matérielle à ce stade.
